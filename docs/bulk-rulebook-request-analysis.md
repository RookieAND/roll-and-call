# 룰북 추가 요청 일괄 제출 분석

최초 분석: 2026-11-09. 시안 및 구현: 2026-11-10.

## 구현 결과

- 후속 UI 피드백을 반영해 공통 정보·덮어쓰기·이름 붙여넣기를 제거했다. 룰북마다 이름·분류·판본·종류·링크를 독립적으로 입력한다. 데스크톱은 본문에 선택한 한 권의 입력 폼, 기존 PageShell 우측 패널에 책 목록·권수·제출 버튼을 배치한다. 모바일/Sheet에서는 목록을 폼 아래에 둔다.
- `다음 룰북 작성`은 현재 책을 검증한 뒤 모든 필드가 비어 있는 새 책을 만든다. 목록에서 책을 오가며 작성한 내용이 보존되고, 항목 삭제 및 최대 20권·책별 오류 표시를 유지한다.
- Server Action은 단건/일괄 모두 배열 처리 경로를 사용하며, 활동 정지와 중복을 서버에서도 검사한다.
- 저장은 같은 groupId의 개별 요청을 하나의 트랜잭션으로 생성한다. 기존 구인 자동 요청의 동일성 규칙을 유지하기 위해 새 전역 UNIQUE 제약 대신 현재 사용자/구인 생성 경로에서 같은 서버 단위의 트랜잭션 advisory lock을 사용한다. 임의 SQL이나 이 잠금 규약을 따르지 않는 외부 생성 경로까지 강제하지는 않는다.
- 관리자 심사·사용자 결과 알림·Discord 메시지는 권별로 유지한다. Discord 전송 실패는 다른 책의 전송을 막지 않는다.
- 개발 전용 미리보기: `/dev/rulebook-requests`. 실제 저장 대신 시안 제출만 수행하며 production에서는 404를 반환한다.
- `0133_bulk_rulebook_requests` 마이그레이션을 생성하고 사용자 요청에 따라 운영 프로젝트 `bnxtukraoqqdhzknuqqp`에 적용했다. 적용 후 nullable UUID 컬럼, `(server_id, group_id)` 인덱스, RLS 유지 및 Drizzle 이력을 조회해 검증했다. 미적용 마이그레이션은 없다.
- 초기 구현의 메모리 Postgres 통합 테스트 5개가 통과했다. UI 단순화 후 입력 모델 테스트 2개, 웹 타입 검사, FSD/토큰 검사 및 Next.js 컴파일·런타임 진단을 통과했다. 실제 Chrome에서 책별 정보 분리, 목록 전환·삭제, 입력/중복 오류, 제출 및 모바일/Sheet 동작을 확인했다. 인증한 실제 사용자로 운영 DB에 제출하는 검증은 수행하지 않았다.

아래는 최초 분석과 추가 확장 시 고려할 사항이다. 공통 기본값과 붙여넣기 제안은 위 후속 피드백으로 대체되었다.

## 권장 방향

사용자는 공통 정보를 한 번 입력하고 여러 책을 한 번에 제출한다. 서버에서는 책마다 기존 `rulebook_requests` 행을 만들고, 같은 제출의 행에 동일한 `group_id`를 붙인다. 관리자는 기존처럼 요청 ID별로 추가·연결·반려한다.

예를 들어 서플리먼트 8권을 제출하면 요청 8개가 생성된다. 3권 추가, 1권 기존 룰북 연결, 1권 반려, 3권 대기가 가능해야 한다. 그룹 전체의 승인 상태는 저장하지 않는다.

묶음이 제출 순간의 편의 기능에 그친다면 DB 변경 없이도 다중 INSERT만으로 구현할 수 있다. 다만 제출 이력 추적과 향후 묶음 표시를 고려하면 기존 일괄 인증과 같은 nullable `group_id`가 비용 대비 적절하다. 별도 신청 그룹 테이블은 현재 요구에는 필요하지 않다.

## 확인 범위와 연결 상태

- 배포 URL은 비로그인 요청에서 `/trpia/join?next=...`로 307 이동한다. 로그인한 실제 화면을 직접 확인하지는 못했고 폼과 동작은 저장소 코드를 확인했다.
- 요청한 프로젝트 URL로 Supabase MCP 전역 등록을 완료했다. 등록 시 자동 OAuth가 `Successfully logged in.`으로 끝났고, 전역 `codex mcp list`에서 `enabled / OAuth`를 확인했다.
- 별도로 실행한 `codex mcp login supabase`도 `Successfully logged in to MCP server 'supabase'.`로 완료했다.
- 현재 대화에서는 새 MCP 서버가 도구 목록에 반영되지 않았다. 리소스 조회도 `unknown MCP server 'supabase'`를 반환했다. 세션을 다시 연 뒤 `/mcp` 및 읽기 전용 조회로 연결을 확인해야 한다.
- 운영 DB의 스키마 차이, 기존 중복 데이터, 권한·정책은 확인하지 못했다. 아래 DB 설계는 저장소 스키마 기준이다.
- Supabase 및 Postgres 스킬은 이미 프로젝트에 있어 추가 설치하지 않았다.

## DB 변경

### 제출 묶음

`rulebook_requests`에 다음 필드 추가를 권장한다.

| 필드 | 타입 | 의미 |
| --- | --- | --- |
| `group_id` | nullable UUID | 같은 제출에 속하는 요청 식별. 기존 행과 구인 자동 요청은 NULL |
| `group_position` | nullable integer, 선택 | 입력 순서 보존이 필요한 경우에만 추가 |

`group_id`는 요청 행마다 default로 만들면 안 된다. 서버에서 한 번 생성해 제출된 모든 행에 같은 값을 넣는다. 한 권 제출에도 그룹 ID를 발급하면 신규 경로를 통일할 수 있다. 기존 데이터는 NULL을 유지하고 화면에서 단일 요청으로 취급한다.

그룹 조회를 구현한다면 `(server_id, group_id)`의 non-unique 인덱스를 추가한다. 순서 필드를 도입하면 그룹 내 순서 중복 방지 제약도 검토한다. 그룹 ID만으로 조회하지 말고 서버 범위와 신청자/관리자 권한을 함께 확인한다.

`outcome`, `processed_by`, `processed_at`, `reject_reason`, `staff_message_id`는 계속 개별 행에 둔다. 책의 카테고리·판본·종류·참고 링크도 제출 시 확정한 값을 각 행에 저장한다. `rulebooks`와 `rulebook_categories` 구조 변경은 필요하지 않다.

별도 부모 테이블은 공통 자료 수정, 그룹 취소, 그룹 알림 재시도, 제출 단위 멱등 키 등 독립적인 그룹 생명주기가 실제 요구가 될 때 고려한다. 이 경우 새 테이블의 RLS와 서버·신청자 일치 제약도 함께 설계해야 한다.

### 중복과 동시성

현재 `중복 SELECT → INSERT`에는 동시 제출 경쟁이 있다. 일괄 저장을 트랜잭션으로 묶는 것만으로 해결되지 않는다.

1. 같은 제출 내부의 중복은 서버 검증에서 먼저 차단한다.
2. 기존 대기 요청 중복 조회는 항목별 SELECT 대신 한 번에 조회한다.
3. 경쟁까지 차단하려면 DB 제약 또는 모든 생성 경로가 따르는 잠금 규약이 필요하다.

현재 사용자 요청의 중복 기준을 그대로 채택한다면, 후보는 `server_id + lower(trim(name || ' ' || edition))`, 조건은 `outcome IS NULL`인 부분 유니크 인덱스다. 다만 이를 즉시 추가하면 안 된다. 구인 자동 요청은 카테고리·판본으로 후보를 먼저 좁히므로 현재 생성 규칙이 완전히 같지 않다. 다른 카테고리의 동명 책도 영향을 받는다.

구현 전에 운영 데이터에서 정규화 키 중복을 집계하고, 전체 생성 경로에 적용할 동일성 규칙을 확정해야 한다. 기존 정책을 유지하는 인덱스를 택한다면 자동 생성 경로도 충돌 시 기존 요청 재조회·재사용으로 수정한다. 사용자 일괄 제출의 충돌은 예외를 정해진 오류 응답으로 변환하고 전체 롤백한다. 제약 없이 애플리케이션 사전 검사만 유지하는 안은 동시 중복을 보장하지 못한다.

등록된 책과의 일치도 별도로 확인한다. 확실하게 일치하는 항목에는 기존 책 선택을 안내하고, 별칭·유사 이름은 경고나 관리자 연결로 남기는 것이 적절하다. 숨김/자작 룰처럼 사용자에게 보이지 않는 책의 정보는 중복 응답으로 노출하지 않는다.

## API 변경

### 하나의 제출 액션

`requestRulebooks` 같은 배열 입력 Server Action을 추가하고, 기존 한 권 요청도 같은 처리 경로에 배열 길이 1로 연결한다. 브라우저에서 기존 액션을 반복 호출하면 일부 성공·알림 중복·불명확한 재시도 문제가 생긴다.

API 입력은 각 항목의 최종 값을 담는 것이 단순하다. 공통값은 UI에서 기본값으로 쓰고 제출 전에 항목별 값으로 확정한다.

```ts
type RequestRulebooksInput = {
  items: Array<{
    clientId: string; // 행별 오류 연결용. DB 권한/요청 ID로 사용하지 않음
    name: string;
    edition: string;
    kind: "core" | "supplement" | "handbook" | "unknown";
    category: string;
    link: string;
  }>;
};
```

카테고리는 1차 구현에서 기존 문자열 계약을 유지할 수 있다. 이름 중복 해석을 줄이기 위해 ID 기반 계약으로 바꾸려면 기존 카테고리 ID와 새 카테고리 이름을 구분하고, ID가 현재 서버에 속하는지 검증한다.

서버 처리는 다음 순서를 권장한다.

1. 인증·현재 서버 멤버십 검증. 활동 정지 사용자의 직접 액션 호출 차단 정책도 명시한다. 현재 전용 페이지에는 차단이 있지만 기존 액션 자체에는 별도 제재 확인이 없다.
2. 배열 1~20권 제한(초기 제안값), 필드 길이·URL·공백·빈 이름 검증. 기존 필드 길이 제한을 유지한다.
3. 내부 중복과 기존 요청/등록 책을 검증하고 `clientId`별 오류 반환.
4. 카테고리를 일괄 해석하고, 서버가 만든 `userId`, `serverId`, `source=user`, `groupId`를 사용해 허용된 필드만 저장.
5. 한 번의 다중 INSERT로 전부 저장. 함께 실행할 DB 작업이 있다면 같은 트랜잭션 사용. DB 충돌도 전체 실패 처리.
6. 커밋 이후 경로 재검증과 `after` 운영진 알림 수행. 알림 실패 때문에 저장 성공을 실패로 바꾸지 않는다.

응답은 기존 `ActionResult`와 호환되는 `error`를 유지하면서 행별 오류와 성공 건수를 확장한다. 예: 성공 시 `{ groupId, createdCount, requests: [{ clientId, id }] }`, 실패 시 `{ error, itemErrors: [{ clientId, field, message }] }`. INSERT의 반환 순서에 의존해 clientId를 매칭하지 않도록 서버에서 요청 ID를 미리 만들거나 명시적 매핑을 사용한다.

### 접수 실패 정책

권장 기본값은 **유효한 항목 전체를 한 번에 접수하며, 오류가 있으면 아무것도 접수하지 않는 것**이다. 중복·잘못된 링크·동시 제출 충돌이 있으면 해당 행을 수정하거나 제거한 뒤 다시 제출한다. 접수 후 관리자 판단은 책별로 독립적이다.

부분 접수를 택하면 성공한 행 제거, 실패한 행 보존, 재시도 식별, 성공 수/중복 수 안내가 모두 필요해 초기 구현이 커진다. 중복 항목을 성공한 것처럼 조용히 제외하지 않는다.

같은 groupId는 그 자체로 재전송 멱등성을 제공하지 않는다. 대기 요청 유니크 제약은 일반적인 중복 클릭을 막지만 응답 유실 뒤 이미 관리자가 처리한 경우까지 식별하지 못한다. 처리 후 재전송도 동일 제출로 응답해야 한다면 별도 제출 키와 저장 구조를 추가로 설계한다.

```text
   참고 링크 형식을 확인해 주세요.

[+ 책 추가]
                       [3권 추가 요청 보내기]
```

- 첫 행은 검색어로 초기화한다. 기존 단건 사용자는 그대로 제출할 수 있다.
- 공통값은 필수가 아닌 편의 기능이다. 여러 카테고리/종류의 책도 행별 수정으로 제출 가능하게 한다.
- 공통값을 상속하는 필드와 직접 수정한 필드를 구분한다. 공통값 변경은 상속 중인 필드에만 반영하고, 개별 값은 유지한다. `공통값 사용`으로 되돌릴 수 있게 한다.
- 같은 룰의 서플리먼트 목록에서는 종류를 한 번 선택하고 이름만 입력하게 한다. 기존 단건처럼 종류 기본값은 `unknown`을 유지하고 임의로 서플리먼트로 바꾸지 않는다.
- 한 줄에 한 이름 붙여넣기를 제공하면 다량 신청의 실제 입력 부담도 줄어든다. 빈 줄 제거·양끝 공백 정리 후 행을 생성하고 검토하게 한다. 이름의 쉼표는 분리 기준으로 쓰지 않는다.
- 목록 중복, 기존 대기, 잘못된 링크를 해당 행에 표시한다. 서버 오류 후 입력과 공통값을 보존하고 첫 오류로 초점을 옮긴다.
- 제출 중 버튼뿐 아니라 행 변경도 제한한다. 성공 시 `3권 추가 요청을 보냈습니다`로 명확히 안내한다.
- 페이지와 Sheet가 동일한 모델·본문을 사용한다. 모바일에서는 펼침 가능한 카드와 고정 제출 버튼을 사용하고 가로로 긴 편집 테이블은 피한다.
- `추가 요청`은 카탈로그 등록 요청이며 소유 인증이 아니다. 기존처럼 등록 후 별도 인증이 필요함을 유지한다.

## 관리자·내 룰북·알림

### 관리자

기존 행과 처리 버튼을 유지한다. 최소 구현은 기존 관리자 화면 변경 없이도 책별 심사가 동작한다. 묶음 맥락을 보여 주려면 데이터 변환/DTO에 groupId를 추가하고 `함께 요청한 8권`과 해당 요청 필터를 제공한다. 승인·연결·반려 API는 그룹을 처리하지 않고 기존 requestId만 받는다. 대기 건수도 제출 수가 아닌 미처리 책 수다.

### 내 룰북

기존 권별 목록은 그대로 작동한다. 묶음 카드를 추가한다면 `8권 중 5권 검토 완료`와 내부 권별 결과를 표시할 수 있다. 현재 결과 조회는 처리 후 30일만 포함하므로, 이 쿼리만으로 그룹 원래 전체 권수를 계산하면 틀릴 수 있다. 묶음 전체 조회 또는 집계가 필요하며, 이를 구현하지 않는 1차 버전에서는 권별 목록을 유지한다.

### Discord 및 사용자 알림

1차 권장안은 **요청마다 운영진 Discord 메시지를 유지**하는 것이다. 저장 커밋 후 각 요청에 대해 독립적으로 전송·메시지 ID 저장을 하고, 한 건 전송 실패가 나머지 전송을 중단하지 않도록 한다. 요청 상한과 Discord 전송 속도 제한을 고려해 제한된 동시성/순차 전송을 사용한다. 기존 알림도 최선 노력 방식이므로 누락을 확실히 복구해야 한다면 outbox/재시도를 별도 범위로 추가한다.

여러 요청 행에 같은 Discord 메시지 ID만 복사하면 안 된다. 현재 결과 수정 로직은 메시지 전체를 특정 한 권의 결과로 바꾸므로 다른 책의 처리 상태가 덮인다. 한 묶음 한 메시지를 원한다면 그룹 집계 기반 렌더링, 동시 수정 제어, 재시도까지 함께 변경해야 한다.

사용자 결과 알림은 기존처럼 권별로 유지한다. 기존 중복 경고의 `추가되면 알립니다` 문구는 주의가 필요하다. 현재 결과 알림은 해당 요청의 userId에게만 보내며, 다른 사람의 대기 요청을 중복으로 막힌 사람을 구독자로 저장하는 구조는 없다. 일괄 제출의 중복 항목에도 자동 알림을 약속하지 않는다.

## 변경 파일과 진행 순서

1. 중복 동일성 및 구인 자동 요청과의 관계를 확정하고 운영 DB에서 기존 중복·정책·스키마 차이를 읽기 전용 확인한다.
2. `packages/database/src/schema/rulebooks.ts`에 groupId 및 필요한 인덱스를 정의하고 프로젝트의 Drizzle 절차로 마이그레이션을 생성·검토한다. 실제 DB 적용은 구현·배포 범위에서 진행한다.
3. database의 rulebooks 모듈에 일괄 생성/중복 조회 command·query와 공개 export를 추가한다. 유니크 제약을 도입한다면 `sync-game-supplement-requests.ts`도 같은 배포에서 수정한다.
4. `features/request-rulebook`의 검증 모델, Server Action, 공유 본문, Screen/Sheet 제출 문구를 배열 입력에 맞춘다. 기존 액션은 공통 경로로 위임한다.
5. 운영진 알림을 각 요청과 매핑하고 실패 격리를 적용한다. 관리자 그룹 표시는 선택적으로 추가한다.
6. 그룹 이력 UI를 추가할 때만 `get-rulebook-records.ts`, `to-my-rulebooks.ts`, 관리자 shapes/types/queries까지 groupId와 집계를 전달한다.

주요 검증: 한 권/20권/빈 배열/상한 초과, 공통값과 개별 수정, 붙여넣기·삭제 후 오류 위치, 내부 중복·기존 대기·등록 책, 다른 서버 카테고리 조작, 동시 중복 제출 시 전체 롤백, 구인 자동 요청과의 충돌·재사용, 알림 부분 실패 후 저장 결과 유지, 같은 묶음의 서로 다른 관리자 결과, 기존 NULL 그룹 요청과 페이지/Sheet의 회귀를 확인한다.

DB 검증은 실제 제약과 트랜잭션이 동작하는 통합 테스트가 필요하다. UI 구현 후에는 실행 중인 Next.js 앱에서 페이지와 Sheet 양쪽을 확인한다. 이 문서는 분석만 수행했으므로 구현 테스트는 실행하지 않았다.
